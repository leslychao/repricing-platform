# Локальные правила стендов и развёртывания

Применять вместе с глобальным `AGENTS.md`. Этот файл задаёт исходные требования для новых веб-проектов с Docker Compose. Разделы Keycloak, OAuth2 Proxy и IDEA применяются при использовании соответствующих инструментов. Не внедрять технологии и не менять существующую архитектуру только ради выполнения правил. Общие требования к качеству, безопасности, проверкам и структуре каталогов определяются глобальным `AGENTS.md`. Особенности конкретного проекта, адреса инфраструктуры и явно согласованные отклонения фиксировать в его канонической документации в `docs/`.

## Стенды и переменные окружения

- По умолчанию предусматривать два стенда: `local` и `dev`. Использовать один основной Compose-файл `deploy/docker-compose.yml`; не создавать его копии ради разных доменов, адресов и портов.
- Использование Compose profiles, дополнительные окружения и особенности выбора стенда, запуска и деплоя определять в канонической документации проекта.
- Для стендов использовать отдельные `deploy/.env.local` и `deploy/.env.dev`. В них хранить только значения, зависящие от стенда, и все секреты конфигурации этого стенда. Общие несекретные значения и состав сервисов задавать непосредственно в Compose. Совпадение секретов на двух стендах не разрешает переносить их в общий файл.
- Реальные env-файлы исключать из Git. В репозитории хранить только шаблоны `.env.local.example` и `.env.dev.example` без секретов. Не включать секреты в исходники, Compose, образы, realm-export, конфигурации IDE, логи и отчёты. Передавать каждому контейнеру только необходимые ему значения.
- Выбирать env-файл явно через `docker compose --env-file`. Не подменять источник подстановок Compose параметром сервиса `env_file`. Не допускать незаметного переопределения выбранного стенда переменными запускающего процесса.
- Проверять обязательные значения до зависимых действий. При отсутствии или пустом значении завершаться с понятной ошибкой без раскрытия секрета; в Compose использовать `${VAR:?сообщение}`. Не задавать встроенные пароли и скрытые значения по умолчанию для адресов серверов.

## Адреса и параметры инфраструктуры

- Адрес dev-сервера задавать переменной окружения стенда, например `DEV_HOST`. Адрес глобального Nginx задавать независимо, например `GLOBAL_NGINX_HOST`. Совпадение адресов не должно связывать их изменение.
- Публичные адреса приложения, адреса привязки и опубликованные порты внутреннего Nginx также задавать в конфигурации стенда. Не дублировать эти значения в скриптах, Compose и `.run`.
- Начальные адреса задавать только в конфигурации конкретного стенда. Общие правила не должны содержать номера серверов, IP, домены или пути конкретного проекта. Перенос стенда на другой сервер не должен требовать изменения скрипта или конфигурации IDE.

## Keycloak, OAuth2 Proxy и начальные пользователи

- Для новых браузерных интеграций с Keycloak по умолчанию использовать OAuth2 Proxy как OIDC-клиент. Существующую архитектуру аутентификации переводить на эту схему в рамках отдельно поставленной задачи.
- Данные сессий OAuth2 Proxy хранить на сервере в Redis (`session-store-type=redis`); в браузере остаётся cookie с билетом сессии. Сохранять защиту cookie, cookie secret и применимую CSRF-защиту, проверку токенов и серверную авторизацию; секреты передавать принятым в проекте способом.
- Для браузерного входа использовать собственную страницу приложения, совмещающую лендинг и форму входа: представление продукта и авторизация образуют единый экран в общем визуальном стиле фронтенда. Страница доступна без авторизации. Стандартные страницы входа Keycloak и OAuth2 Proxy пользователю не показывать.
- Кастомный интерфейс сохраняет штатный OIDC-поток и ответственность Keycloak за аутентификацию; его можно реализовать собственной темой Keycloak в дизайне приложения. Не заменять OIDC самодельной проверкой паролей ради размещения формы во фронтенде.
- Выход должен завершать сессию приложения, включая OAuth2 Proxy, и соответствующую SSO-сессию Keycloak, после чего автоматически возвращать пользователя на собственную страницу лендинга и входа. Не показывать подтверждение выхода, стандартную страницу Keycloak или отдельный экран «Вы вышли»; не допускать автоматического повторного входа за счёт оставшейся сессии.
- В обычном сценарии входа и выхода не добавлять промежуточные страницы, выбор единственного провайдера и дополнительные подтверждения. Ошибки входа показывать на собственной странице входа. Необходимые служебные перенаправления OIDC допустимы без отдельных пользовательских экранов. Это требование не разрешает отключать обязательные проверки безопасности; если действующая политика требует отдельного действия пользователя, противоречие разрешать явно до реализации.
- В `local` и `dev` заранее подготавливать в realm приложения две управляемые учётные записи: `test` и `admin`. Профили включать в поставляемую конфигурацию realm; пароли получать из обязательных переменных окружения стенда, например `KEYCLOAK_TEST_PASSWORD` и `KEYCLOAK_APP_ADMIN_PASSWORD`. Последнюю отделять от bootstrap credentials администратора Keycloak.
- Обе записи должны быть готовы к работе сразу после входа: `enabled=true`, `emailVerified=true`, постоянный пароль (`temporary=false`), пустой `requiredActions` и полностью заполненный валидный профиль. Не требовать подтверждения email, смены пароля, заполнения профиля, настройки MFA или других дополнительных действий. Учитывать политики realm, клиента и authentication flow; не ослаблять защиты остальных пользователей ради этих записей.
- Учётной записи `admin` назначать административные права приложения, без административных прав Keycloak. `test` получает только права для предусмотренного тестового сценария. Членство и разрешения подготавливать через штатного владельца доступа приложения в соответствии с его моделью авторизации. Имя пользователя не заменяет проверку прав на бэкенде.
- Подготовку выполнять идемпотентно, без пересоздания realm, дубликатов и изменения посторонних пользователей. Совпадение логина с неуправляемой записью не разрешает заменять её или сбрасывать пароль. В production такие учётные записи автоматически не создавать.

## Nginx и публичный вход

- Во всех Compose-окружениях использовать внутренний Nginx отдельным сервисом и единственной точкой публичного входа для всего трафика приложения, который он может корректно проксировать. Для HTTP(S)/WebSocket использовать HTTP-модули, для поддерживаемых TCP/UDP-протоколов — `stream`. Сохранять проверки доступа и протокольные гарантии на всех предусмотренных входах, включая аутентификацию и поддерживаемые служебные протоколы.
- При доступе через инфраструктуру стенда использовать существующий глобальный Nginx, управляемый вне репозитория и Compose приложения. Сохранять маршрут: клиент → глобальный Nginx → внутренний Nginx → компоненты приложения. На глобальном Nginx выбирать приложение и транспорт; внутренней маршрутизацией владеет Nginx приложения. Не направлять публичный трафик напрямую к компонентам.
- Публичный TLS завершать на глобальном Nginx, когда это совместимо с протоколом и требованиями защиты. Использовать существующие сертификаты и централизованное продление; не выпускать дубли сертификатов и не копировать публичные приватные ключи в сервисы без подтверждённой необходимости. Сохранять требуемые внутренний TLS, mTLS и сквозное шифрование. TLS passthrough использовать при обоснованной необходимости завершать TLS у получателя.
- До выбора проксирования проверять сохранение значимых свойств протокола: исходных адресов, сессий, двунаправленного обмена, динамических портов, таймаутов и ограничений доступа. Прямой публичный вход допускать только при подтверждённом техническом ограничении после проверки поддерживаемой схемы через Nginx; причину, границы исключения и защиту описывать в документации проекта.
- На `local` без глобального Nginx использовать необходимые опубликованные порты внутреннего Nginx, с привязкой к loopback для доступа только с локальной машины. При доступе через глобальный Nginx ограничивать источники обращений к внутреннему. Внутренние и relay-порты не публиковать без необходимости.
- Для браузерного входа согласовывать публичный URL, Host/Origin, OIDC callback и forwarded headers; доверять переданным заголовкам только от предусмотренного прокси. Проверять используемый приложением WebSocket.
- Внутренние обращения сервисов друг к другу, к БД и внутренний обмен медиаданными не требуется проводить через Nginx, если они не образуют отдельного публичного входа.

## Минимальный деплой dev

- Использовать один целевой shell-скрипт `deploy/deploy-dev.sh`. Для dev в доверенной локальной сети обращаться к Docker API сервера из `DEV_HOST` по TCP-порту `2375` без TLS. Ограничить доступ доверенными машинами деплоя; не публиковать этот порт в Интернет. Это закрытый канал управления Docker, он не образует публичный вход приложения и не отключает его HTTPS.
- Скрипт последовательно проверяет конфигурацию, подготавливает необходимые образы и применяет основной Compose к выбранному Docker-хосту. Использовать штатные команды сборки, не копировать их внутреннюю логику. Ошибка обязательного шага останавливает деплой с ненулевым кодом; успех требует предусмотренной проверки готовности сервисов.
- Не включать в скрипт бэкапы, восстановление, очистку томов, `prune`, настройку Docker daemon или глобального Nginx. Не создавать универсальный механизм управления инфраструктурой. Обычный повторный деплой должен сохранять данные и существующий realm.
- Учитывать расположение файлов при удалённом Docker API: файлы для монтирования должны быть доступны на Docker-хосте либо входить в соответствующие образы. Путь на машине запуска не означает наличия файла на сервере.

## Переносимые конфигурации IDEA

- Общую конфигурацию запуска хранить в `.run/`. Она вызывает тот же `.sh` и выбирает env-файл и Compose, не дублируя деплой, адреса и секреты. Запуск из терминала и CI не должен зависеть от IDEA.
- Все проектные пути задавать через `$PROJECT_DIR$`: например, `$PROJECT_DIR$/deploy/deploy-dev.sh`, `$PROJECT_DIR$/deploy/.env.dev` и `$PROJECT_DIR$/deploy/docker-compose.yml`. Рабочая директория — `$PROJECT_DIR$`; передаваемые относительные пути разрешаются от явно заданной базы.
- Не сохранять абсолютные пути конкретного checkout, имена учётных записей Windows и соответствующие им пути WSL. Внутри `.sh` разрешать пути к файлам проекта относительно расположения скрипта и корректно обрабатывать пробелы.
- В Windows выполнять `.sh` в Linux-среде. Не создавать параллельные PowerShell- и batch-версии того же деплоя. Перенос checkout и запуск другим пользователем не должны требовать редактирования файлов проекта.

## Бэкапы и объём работ

- По умолчанию не вводить никакие бэкапы и восстановление из резервных копий; это правило действует для всех версий и окружений. Добавлять их только по отдельному явному требованию пользователя.
- Без такого требования не добавлять сервисы и скрипты резервного копирования, фоновые задания, расписания, хранилища и политики хранения копий, мониторинг бэкапов, проверки и тренировочные восстановления. Не включать их в обязательные шаги разработки, CI/CD или деплоя и не создавать заготовки «на будущее». Не заявлять неподтверждённые RPO/RTO.
- Границы версии фиксировать в канонической документации проекта. Изменение этих общих правил само по себе не отменяет уже принятых требований к сохранности и восстановлению данных существующего проекта.
- Отсутствие бэкапов не отменяет постоянное хранение рабочих данных, безопасные миграции, сохранение данных при повторном деплое и необходимые гарантии внешних операций.

## Проверка

- Проверять итоговую конфигурацию обоих стендов без раскрытия секретов, отказ при отсутствии обязательных значений и отсутствие встроенных адресов. Смена dev-сервера должна требовать только изменения конфигурации стенда.
- Проверять запуск из IDEA после переноса checkout, в том числе в путь с пробелами. Проверять повторный деплой и идемпотентную подготовку пользователей с сохранением данных.
- При использовании Keycloak проверять реальный браузерный вход отдельно под `test` и `admin`: отсутствие дополнительных действий, предусмотренные права приложения и хранение сессий в Redis. Для публичного входа проверять маршрут через оба Nginx и значимые свойства используемых протоколов; для браузера — OIDC callback и используемый приложением WebSocket.
- Для собственной страницы лендинга и входа проверять доступ без авторизации, успешный вход, отображение ошибки входа и выход с возвратом на эту же страницу. Во всём маршруте не должны появляться стандартные страницы Keycloak или OAuth2 Proxy, промежуточные экраны и подтверждения. После выхода защищённые страницы и API должны требовать новую аутентификацию; прежние сессии приложения и Keycloak не должны восстанавливать доступ.
- Разбор Compose, сборка, healthcheck и получение токена без браузера не заменяют проверки пользовательского маршрута.
